# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Overview

`Labelled Links` labels the links between notes. A link from `A` to `B` is an arrow, and a backlink is the same arrow seen from `B`. This plugin gives that arrow a label (`A --employee--> B`) and shows the inverse label from the other end (`B --employer--> A`).

It is meant to sit **alongside** `Breadcrumbs`, the incumbent typed-links plugin, not replace it. Do not duplicate hierarchy navigation, transitive inference or diagrams. The gaps this plugin fills are the ones no existing plugin covers:

- the label shown on the link itself, in the editor and on hover;
- a typed query API with incoming queries, change events and published typings;
- one pane listing every relation of a note in both directions, with inverse labels, plus the plain links and backlinks;
- a simple registry where each label pair is declared once;
- every link-valued property read as a relation, with no setup.

## Current state

**The relation index, the registry, the relations pane, the link badges and the API are built.** The repo was generated on 2026-10-17 with `create-obsidian-plugin` (preset `all-in-one`, CodeMirror editor extensions, CSS, desktop and mobile, the unofficial API subset). Its answers are in `.create-obsidian-plugin.json`, so re-running the generator in this folder updates every file not edited by hand. The generator's sample commands, settings, editor suggest and editor extensions are gone. Unit-test coverage is gated at 100%. The demo vault has a note per headline feature: relations, the registry, the pane, the badges and the API (`05 For plugin developers`, whose buttons look the API up with `findPluginApi` through a copy of the `api.d.ts` declarations in `demoSetup.ts`). The README follows the shared plugin skeleton, with a `## For plugin developers` section, the screenshot block and a `## Changelog` link to `CHANGELOG.md`.

- `src/relation-registry.ts` parses the `relationDefinitions` setting (`label <-> inverse`, `label <-> label`, a lone `label`) and answers inverse labels, ignoring case.
- `src/relation-extractor.ts` turns a note's cached metadata and text into its references, each with its label or `null`. The metadata cache does not record inline fields, so they are read from the text, and so is a hidden label: a `%%:label%%` comment right after a body link (`[[B]]%%:child%%`), which wins over an inline field the link sits in. The `:` keeps an ordinary comment after a link from being read as a label. Obsidian caches a property value holding several links (`"[[A]], [[B]]"`) as one link to `A]], [[B`, so such a key's cached entry is replaced by the links `parseFrontmatterLinks` finds in the value.
- `src/views/relations-view.ts` is the relations pane (`labelled-links-relations`), opened in the right sidebar by **Open relations pane**. It follows the active note through `file-open` and redraws on the index's `changed` event when the event names that note. Labelled relations are grouped by label ignoring case, incoming ones under their inverse label; plain links and backlinks get the source line as a snippet, read with `cachedRead`, and a newer redraw drops an older one still reading. Rows open with `openLinkText` and fire `hover-link` from a registered hover source.
- `src/link-badge.ts` builds the badge both views put after a labelled body link: the label, with a two-line tooltip (also its `aria-label`) naming the relation and its inverse from the registry. Properties get no badge, since the property name already shows the label beside the link, and neither do plain links or embeds. A cached offset is trusted only while the note's text still holds the reference's `original` there, because the metadata cache lags typing.
- `src/editor-extensions/link-badge-view-plugin.ts` is the Live Preview half, a `ViewPlugin` reading the note from `editorInfoField`. Edits map the badges, and the index's `changed` event for the note rebuilds them. Source mode shows none. `obsidian`'s typings resolve `@codemirror/state` to its CommonJS declarations, so `editorInfoField` and `editorLivePreviewField` are `castTo` the ESM `StateField` type.
- `src/link-badge-reading-view-component.ts` is the Reading view half: a post-processor pairing a section's `a.internal-link`s with its references by `data-href`, in order. After an index change, a reading view whose note's badges now differ from what it rendered is re-rendered once, debounced. Re-rendering every reading view on every change swapped the DOM under the pointer.
- `api.d.ts` (repo ROOT) is the consumer-facing declaration file, following `More Events`: `LabelledLinksApi` (`getRelations(pathOrFile, { direction?, label? })` and `getInverseLabel(label)`), the plain-data `LabelledLinksRelation`, and the `labelled-links:relations-changed` event with its `{ paths }` payload as a `Workspace.on` augmentation. It imports from `obsidian` only. Its interface members are function properties, because the shared lint config forbids method signatures; only the `Workspace.on` overload stays a method, since a property does not merge into an overload set.
- `api-contract.ts` (repo ROOT) is `LABELLED_LINKS_API_CONTRACT`, a real `input` and `output` schema for each method, built from `@mnaoumov/typescript-lib/api-contract` with the vendor `labelled-links`. A relation's `reference` is checked for `link`, `original` and an optional `displayText`, and its other members (`key`, `position`) are let through. Both root files are added to the ESLint source files in `scripts/eslint-config.ts`; without that, `api.d.ts` matched only the `**/*.d.ts` object, which has no parser, and failed to parse as JavaScript.
- `src/labelled-links-api.ts` holds the event-name constant, `PLUGIN_API_CONTRACT` and `PLUGIN_API_VERSION` (`1.0.0`, the contract's own version), and `src/labelled-links-api-impl.ts` is the delegate over the index. It maps the internal `RelationDirection` enum to the published string literals and `structuredClone`s each reference, so a consumer never holds the metadata cache's objects. `Plugin.getPluginApis()` declares it, and `onloadImpl` re-triggers the index's `changed` event on `app.workspace` under the published name. The event name and the version are a wire contract, which `src/labelled-links-api.test.ts` asserts as literals.
- `npm run capture:screenshots` rewrites `images/screenshots/`: five desktop and five mobile frames, the directory's cap per form factor. Its two projects (`capture-screenshots:desktop`, and `capture-screenshots:android` on the 900x1600 `obsidian_screenshots` AVD) open the demo vault through `scripts/screenshots-global-setup.ts`, which also seeds the harness plugin, so the registry shot sets the registry with `lib.configureCommunityPlugin`. The desktop suite sizes the real window to 1200x800 first, because the capture pins its viewport only for the frame, and a tooltip placed against another size floats away from its badge. The badge tooltip is raised with `displayTooltip`, since a hover raises none in the test instance. A desktop re-run reproduces every frame byte for byte.
- The desktop, Android and performance integration projects seed `obsidian-dev-toolkit`'s integration-test harness plugin (`scripts/vitest-global-setup.ts`, plus `src/@types/obsidian-integration-testing.d.ts` for the types), so a closure's `lib` carries `findPluginApi`. The demo-vault project does not seed it, so it keeps the plain `vitest-setup`. Integration suites share one vault per worker, and the index suite counts every relation in it, so a suite that creates notes deletes them again.
- `src/relation-index-component.ts` keeps every note's references, resolved, in an outgoing and an incoming map. A metadata `changed` event patches one note. A vault `create`, `rename` or `delete` only marks the resolution stale, and the next query re-resolves from memory, so a folder rename does not re-resolve once per file. Incoming labels come from the registry at query time, so a registry change re-indexes nothing. Plain links and backlinks come from the same index with a `null` label, rather than from `getBacklinksForFileOrPath`, so a relation and a plain link to the same note always agree on how the link resolved.

## Design

This is the starting point the owner approved. Refine it as the build goes.

1. **Source of truth is plain syntax only.** Every link-valued property is a relation, with no setup: `employee: "[[B]]"`, and lists too. So is every `label:: [[B]]` inline field. There is no plugin-only syntax, so a vault stays readable without the plugin.
2. **A relation registry in settings.** It holds pairs (`employee` <-> `employer`, `child` <-> `parent`), symmetric labels (`spouse`, `sibling`) and labels with no inverse. Inverses are computed in memory and **never written into notes**.
3. **A relations pane.** For the active note it shows outgoing and incoming relations grouped by label, with each incoming relation listed under its inverse label. Plain links and backlinks go in an *unlabelled* group, with a context snippet.
4. **Editor and hover.** A small badge with the label sits on each labelled link, in Live Preview and in Reading view. A hover shows the relation and its inverse.
5. **API.** `getRelations(file, { label?, direction? })` plus change events, published through `@mnaoumov/obsidian-lib`'s plugin-API contract with typings, so other plugins and scripts can query relations.
6. **Index.** Build it on the metadata cache and backlinks, and update it incrementally rather than rebuilding it per query.
7. **Later.** Graph edge labels or colors, a Bases column, and an optional import of `Breadcrumbs` edge-field pairs.
